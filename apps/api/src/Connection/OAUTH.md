# Owner-managed OAuth for MCP connections

Start with owner-authorized OAuth for one interoperable profile. A confidential client registered with the selected server’s authorization provider uses the authorization code grant with S256 PKCE, an exact HTTPS callback, protected-resource and issuer metadata, RFC 9207 issuer identification, and a resource indicator. Qualify this profile with a synthetic provider before enabling it on a deployment. Continue to offer static bearer credentials for servers that accept them.

[OAuth security best current practice](https://www.rfc-editor.org/rfc/rfc9700.html) · [OAuth resource indicators](https://www.rfc-editor.org/rfc/rfc8707.html) · [Protected resource metadata](https://www.rfc-editor.org/rfc/rfc9728.html) · [Authorization response issuer](https://www.rfc-editor.org/rfc/rfc9207.html) · [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

## Owner experience

The owner opens an MCP connection in a vault, chooses the server and approves the requested permissions. An owner-authenticated request starts a short-lived, single-use authorization attempt bound to the deployment, vault, credential, and initiating browser session. The provider returns a top-level GET to the exact callback on the dashboard origin. The callback verifies the single-use state, exact issuer, and a short-lived, host-bound HttpOnly Secure SameSite=Lax attempt cookie. The ordinary owner session cookie remains SameSite=Strict. Atomically consume the callback state as private custody stages the code. Use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, omit callback queries from logs, and redirect to a clean same-origin confirmation URL without OAuth parameters. The confirmation page loads no third-party assets. An authenticated owner-session POST from that page claims the pending attempt exactly once before exchanging the code. It must match the owner session that started the attempt. A callback without the attempt cookie, an exact RFC 9207 `iss`, or the later owner session cannot enable the connection. A completed connection shows its target, approved scope, and connection status. The owner can reauthorize or disconnect it from the vault.

A selected session uses the existing vault and credential binding. An agent can call authorized tools through that binding. It cannot start owner authorization, widen consent, read tokens, or change the destination. Static token rotation remains an explicit owner action.

## Custody and lifecycle

The existing Vault owns connection metadata and lifecycle. The vault’s private credential custody owns the callback attempt, client secret, access and refresh tokens, expiry, and a generation counter. Public credential reads and domain events expose status and identifiers. They do not carry OAuth secrets or provider response bodies. Check the destination before the first metadata fetch and again for every discovered endpoint. Require HTTPS, pinned issuer and normalized resource, allowlisted public endpoints, and egress that rejects private, local, or otherwise prohibited addresses at connection time. Refuse discovery and endpoint redirects. Send the same canonical `resource` on authorization, code exchange, and refresh. Refuse unexpected scope changes.

| State | Behavior |
| --- | --- |
| Authorization pending | Hold the short-lived state and PKCE verifier in custody. A denied, expired, or replayed callback cannot enable outbound requests. |
| Ready | Attach an unexpired access token only inside the vault-owned MCP connection. Apply the environment’s ordinary network policy to the session’s MCP calls. |
| Refresh due | Serialize refresh by credential generation. Persist a dispatch intent conditional on the live generation before contacting the token endpoint. Concurrent requests share the in-flight operation. Commit the returned token pair and clear the intent atomically, then discard cached client sessions for that credential before admitting new requests. An unresolved intent recovered after restart requires owner reauthorization. |
| Reauthorization required | Stop using the grant on a definitive invalid or revoked refresh. Treat a lost response after a rotating refresh was attempted as unresolved and require reauthorization. A provider might have consumed the previous token. Expose a stable, secret-free refusal. |
| Disconnected or erased | The committed vault or credential archive or deletion is authoritative immediately. Every token use and late result must respect that state even while the private seal and erasure are pending. Mark the custody generation ended before clearing tokens and pooled clients. A racing callback or refresh can commit only against its original live generation. Owner disconnection attempts provider revocation where supported and completes local erasure independently. |

Transient errors may leave the original unexpired access token available when custody can establish that refresh was never dispatched. Never replay an ambiguous rotating refresh or automatically repeat an MCP tool invocation because an authentication failure arrived after dispatch. Authorization code, token endpoint, and tool-call failures expose bounded messages without credentials, callback parameters, or provider payloads.

## Verification and activation

The integrated provider fixture must exercise callback replay, crossed browser sessions, missing callback cookie or same-site owner session, missing or mismatched callback issuer, private or mismatched metadata target, expired code, one refresh for simultaneous calls, a rotating response lost after dispatch, restart after dispatch or after response but before commit, revoked consent, and refresh or callback racing with archive or deletion. Check that a refreshed token is sent only to the authorized resource, earlier pooled clients are discarded, and no fixture secret appears in public responses, transcripts, events, or diagnostic logs.

Model the generation and erasure transitions in Alchemy and verify that erased connections cannot be restored by late effects. Exercise the owner flow through the real dashboard and API and run MCP calls through the vault binding. Deployment activation requires a stable HTTPS callback registered with the provider and verified erasure, restart, and failure behavior on the native Worker. Until then the release evidence continues to identify managed refresh as unqualified.

## Local custody qualification

The SQLite fixture opened new owner instances on the same database and used a counted in-process provider. Two concurrent refresh callers shared one provider request. A failed intent write made zero calls. An unresolved intent required reauthorization after reopening, with no outbound call when the send had yet to start and one total call when the provider reply was lost or replacement failed to commit. Reopening after a committed rotation returned the new grant. Definitive revocation cleared the old grant. A late result after credential erasure, vault seal, or a newer authorization never replaced the current grant.

Proceed with the owner-authenticated browser callback and metadata discovery for the single supported profile. The fixture qualifies the transaction and restart behavior in local SQLite. Production acceptance still requires the Alchemy lifecycle proof, the native Worker and vault binding, the registered HTTPS callback, the owner UI, and an MCP invocation that uses the refreshed grant only at its authorized resource.

## Local callback qualification

The dashboard now signs a distinct browser binding for each login. A local callback fixture used that binding together with a host-bound, short-lived attempt cookie. It accepted the exact issuer and redirect, staged the code before redirecting to a clean confirmation URL, and allowed one authenticated claim. Crossed sessions, missing cookies, expired attempts, and untrusted metadata produced no token exchange.

The SQLite owner preserved callback and grant state across closing and reopening a database file. Its expiry sweep removed expired attempts. Credential erasure and vault sealing deleted staged attempt secrets in the same transaction and refused late results. Code claims survived a failed token commit without leaving a grant. Provider access used a counted in-process transport with pinned endpoints. Native verification still needs the registered HTTPS callback, browser cookie behavior across the provider redirect, connection-time network policy, and the vault-owned MCP invocation before enabling the flow.
