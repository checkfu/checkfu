# Webhook delivery inspection

## Field inventory

An operator starts with a registered endpoint, selects a recent delivery, and opens its diagnostics. The four reads already exist in the authenticated API. Their dashboard SDK operations are `webhooks.list`, `webhooks.retrieve`, `webhooks.deliveries.list`, and `webhooks.deliveries.retrieve`. [Webhook API](../packages/sdk/src/Api.ts#L3392) · [Delivery API](../packages/sdk/src/Api.ts#L3538) · [Delivery resource](../packages/sdk/src/Api.ts#L1282)

| Operator question | API source | Display |
| --- | --- | --- |
| Which endpoint am I inspecting? | `GET /v1/webhooks`, then `GET /v1/webhooks/{webhook_id}` | Current endpoint `id`, status, and only the hostname parsed from its `url`. In detail, show its subscribed `event_types`. The displayed host describes the current definition. |
| Which delivery should I open? | `GET /v1/webhooks/{webhook_id}/deliveries` | `id`, `event_type`, `created_at`, status and `attempt_count` out of `max_attempts`. Use the endpoint ID and delivery ID in the detail route. |
| Did the receiver answer? | `GET /v1/webhooks/{webhook_id}/deliveries/{delivery_id}` | Show `last_attempt_at` as the recorded attempt time and label the typed `last_outcome`. Show `last_http_status` alongside a matching HTTP outcome class. |
| When will it retry or when did it finish? | The same delivery resource | `next_attempt_at` when present and pending, and `completed_at` when available for a terminal record. Show `updated_at` in detail for freshness. |
| Is this the same event as another delivery? | The same delivery resource | Show `event_id` in detail. Distinct delivery IDs can share it. The response has no source delivery ID, operator identity, or per-attempt timeline. |

Use allowlisted outcome labels for `http_2xx`, `http_redirect`, `http_4xx`, `http_5xx`, `timeout`, `network_error`, and `invalid_destination`. A null outcome has no recorded diagnostic class. Suppress the HTTP status for a non-HTTP outcome. An invalid destination can be recorded after an earlier request without clearing the earlier HTTP status. The dashboard should omit raw `last_error`, and should only render the parsed hostname from the configured URL. Request and response bodies, headers, signing material, and the historical destination are outside the display contract. The delivery response carries no payload or signature. Creation and key rotation return their own one-time signing material. [Outcome schema](../packages/sdk/src/Schemas.ts#L990) · [Endpoint and delivery resources](../packages/sdk/src/Api.ts#L1239) · [Delivery serializer](../apps/api/src/Http/WebhooksHandlers.ts#L104) · [Invalid destination transition](../apps/api/src/Webhooks/WebhookDeliveryEngine.ts#L779)

Keep the dashboard's existing signed-in route and same-origin `/v1/` request path. The dashboard Worker strips caller credentials before forwarding and supplies the deployment bearer only for a valid dashboard session. API authentication then enforces access. The Worker also checks origin for unsafe methods, including a future redelivery POST. Delivery reads are keyed by the endpoint, and the server requires a live endpoint record for either read. Paused and automatically disabled endpoints remain inspectable. Use the existing sign-in path for expired sessions and clear cached endpoint and delivery data on sign-out. The public contract exposes the existing deployment authorization and no separate delivery capability. ## Inspection states

Add **Webhooks** to the signed-in navigation. `/webhooks` lists endpoints. `/webhooks/{webhookId}` opens endpoint status and recent delivery history. `/webhooks/{webhookId}/deliveries/{deliveryId}` opens a specific delivery. The breadcrumb links back to the same endpoint. Render an ordinary table of delivery links and a labelled detail view. Move focus to the new heading on navigation and restore the relevant list context when going back.

| State | View and behavior |
| --- | --- |
| No endpoints | “No webhook endpoints” once the cursor is exhausted and no endpoints were found. |
| Empty delivery history | “No recent deliveries” under a known endpoint. Recent history can be empty after retention. |
| Loading or transient error | Keep endpoint context and any loaded rows while loading another page or refreshing. For failed reads show Retry with the same endpoint, delivery ID or cursor. Initial loading has a short status label. |
| Pending | “Queued” at zero attempts. After an attempt, show “Retry scheduled” when `next_attempt_at` is present. Keep the last recorded outcome visible with its timestamp. |
| Succeeded | “Delivered”, backed by status `succeeded` and the receiver's 2xx response when recorded. This acknowledges the HTTP request. Downstream processing is unknown. |
| Failed | “Failed”, with the typed outcome, matching HTTP status when present, last attempt, and attempts used. A redirect can fail immediately. A transient response can continue to retry while the record is pending. |
| Skipped | “Skipped”, with any recorded attempt and completion fields. Use the current endpoint's status only for current context. The response has no typed historical skip reason. |
| Missing or expired delivery | A 404 can mean the delivery was removed, belongs to another endpoint, or never existed. Use “Delivery unavailable” and a link to the endpoint's history. A deleted endpoint has no available history route. |

The endpoint directory has its own opaque cursor. Request `order=desc` for newest-first browsing. The API otherwise defaults to oldest first with 50 endpoints per page. Round-trip the endpoint list's `next_page` as `page` until null, separately from any delivery history cursor. An empty hydrated page with a next cursor still has a way to load more. Show the empty directory state only once no rows are available and the chain ends. [Endpoint pagination](../apps/api/src/Http/WebhooksHandlers.ts#L257) · [Listing hydration](../apps/api/src/Http/Listing.ts#L165)

The delivery list is newest first, ordered by creation time and delivery ID. Pass the opaque `next_page` back as `page` and offer **Load earlier deliveries** until the API returns null. Keep the original page on errors and preserve focus on the load control. A refresh from the top starts a fresh cursor chain. Reuse the selected detail route and deduplicate visible rows by delivery ID, since separate attempts can share an event. Clear old pages when switching endpoint. The engine removes terminal records after 14 days from creation or when more than 500 terminal records are retained. Pending records have their own queue limit. [Cursor and retention rules](../apps/api/src/Webhooks/WebhookDeliveryEngine.ts#L525) · [Pruning](../apps/api/src/Webhooks/WebhookDeliveryEngine.ts#L595)

## Redelivery

The inspection release needs only reads. A later operator action can call `POST /v1/webhooks/{webhook_id}/deliveries/{delivery_id}/redeliver` once on an explicit confirmation through `webhooks.deliveries.redeliver`. The action explains that it resends the original event to the endpoint and may repeat downstream side effects. Show the event type, latest observed hostname and selected delivery ID in the confirmation. Delivery uses the endpoint configuration in effect when it runs. The API requires the endpoint to be active. A 409 means the endpoint must be resumed or reactivated before another request. A 404 can mean the endpoint or delivery is unavailable. [Redelivery API](../packages/sdk/src/Api.ts#L3576) · [Status checks](../apps/api/src/Http/WebhooksHandlers.ts#L524)

The HTTP contract is 201 with a new delivery resource. The dashboard SDK exposes JSON from a successful response. Validate the returned delivery and require a usable new ID before assigning acceptance to that request. Link to that ID. Use **Redelivery queued** for a pending response and **Redelivery accepted** if the row already reached a terminal status. Display the actual delivery status from the returned resource and later reads. In production it can remain pending after 201. An auto-draining test fixture can already return `succeeded` in the resource. The original delivery remains its own record. The server uses the same event ID and payload, and the delivery engine tests show the signed event ID stays the same. [Worker scheduling](../apps/api/src/Webhooks/WebhookDeliverer.do.ts#L268) · [Engine replay](../apps/api/src/Webhooks/WebhookDeliveryEngine.ts#L561) · [HTTP fixture](../apps/api/test/Api.webhooks.test.ts#L284) · [Stable event ID fixture](../apps/api/test/WebhookDeliveryEngine.test.ts#L819) · [Dashboard SDK decoding](../packages/sdk/src/Fetch.ts#L275)

Disable the confirmation while the request is in flight and guard synchronous duplicate clicks. Refresh the endpoint, first history page and new detail after a successful response. The API has no redelivery idempotency input or client correlation field, and a second accepted POST can queue another delivery. After a dropped response, an unreadable success or missing ID, or an intermediary error that could have followed the commit, show **Redelivery could not be confirmed** and refresh the endpoint and recent history before allowing another deliberate request. A newer row with the same event ID can come from another operator or request. Use the refresh for inspection and keep the previous request marked uncertain unless its own response returned an ID. A second submission requires a fresh confirmation that gives the duplicate-delivery consequence. Keep the ambiguous state and refresh available while reads fail. Refresh performs reads only, including when an error message suggests retrying the request. ## Acceptance cases

| Synthetic exercise | Expected behavior |
| --- | --- |
| Open endpoint with no recent deliveries | Empty state appears only after a successful empty list. Transient error keeps Retry and no false empty result. |
| Page through the endpoint directory | With explicit descending order, reach endpoint IDs beyond the first page using exactly its returned cursor. An empty page with a next cursor supports continued browsing. The endpoint directory keeps a separate cursor from delivery history. |
| Load two delivery pages, refresh, and change endpoints | Send the opaque cursor unchanged and preserve newest-first order. Two rows sharing an event ID remain distinct. Refresh starts a new cursor chain. Changing endpoint clears the previous cursor, rows and selected detail. |
| Open the failed delivery through its list link | Show the permitted metadata and typed reason. The endpoint URL fixture includes a path and query marker, and the delivery has an error marker, so the fixture asserts that those markers and any payload or signature fields never appear. |
| Open paused, redirect-disabled or failure-disabled endpoint | List and detail remain readable. The endpoint status is announced and a future redelivery control stays unavailable. |
| Navigate to removed endpoint, retained delivery under the wrong endpoint, or expired delivery | Use the appropriate unavailable state and link back. A 401 uses the existing sign-in flow. Read requests stay on the dashboard origin. |
| Read a zero-attempt pending record, retrying record, success and skipped record | Show the correct status, times and attempts from the fixture. A missing status code appears as absent. A 2xx fixture ties “Delivered” to the delivery record and its response. An invalid destination fixture carrying an older HTTP code suppresses that code. |
| Double-click confirmation and receive 201 with pending | Capture one POST for the chosen delivery. Show queue acceptance and the new ID. A later GET advances the new row to succeeded or failed. The previous row retains its original state. |
| Drop the response after the server accepted the POST or omit its new delivery ID | Show uncertainty, issue only reads while refreshing, and keep separate IDs for fresh rows sharing the event. A repeated POST requires another confirmed action. |
| Disable the endpoint or expire the original before the POST | Show the existing 409 or 404, refresh the affected view and return focus to a reachable control. Preserve the server's authority over the write. |

The engine retry fixture first exhausts six failures, creates a new record, then drains it successfully while the original remains failed. The SDK and API fixture confirm the 201 contract and shared event ID. The dashboard's request recorder is suited to exercising the listed reads, the injected transport failure and the single-POST oracle when the UI is implemented. ## Decision

Start with authenticated read-only inspection. It answers whether an endpoint is receiving requests, why a delivery failed at the HTTP layer, and whether it will retry. It uses existing API operations and adds dashboard routes with an explicit display field list. Include any implemented routes in the first-view bundle budget.

Evaluate redelivery independently after operators can diagnose the original failure. Turn it on only when the dashboard can distinguish queue acceptance from delivery success and preserve uncertainty across a lost response. A stronger guarantee around reconnecting after a lost POST would require an idempotency or correlation contract. Keep endpoint management and access to delivery contents as separate decisions.
